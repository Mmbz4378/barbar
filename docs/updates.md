# به‌روزرسانی خودکار

از نسخهٔ **۱۴.۲.۰** رشن خودش به نسخه‌های بعدی می‌رود: نسخهٔ تازه را از
GitHub Releases پیدا می‌کند، دانلود و بررسی می‌کند، نصب می‌کند و اگر
مشکلی پیش بیاید به نسخهٔ قبل برمی‌گردد. دیگر لازم نیست ZIP را دستی روی
هاست استخراج کنید.

> **یک بار دستی:** نصبی که هنوز ۱۴.۲.۰ نیست، به‌روزرسان ندارد. همین یک بار
> بستهٔ ۱۴.۲.۰ را مثل قبل روی هاست استخراج کنید و از `/doctor.php` مهاجرت‌ها
> را اجرا کنید. از آن به بعد همه‌چیز خودکار است.

## برای انتشاردهنده (شما)

### انتشار یک نسخهٔ تازه

1. تغییرات را در شاخهٔ اصلی merge کنید.
2. در فایل `VERSION` شمارهٔ تازه را بنویسید (مثلاً `14.3.0`) و در
   `CHANGELOG.md` بخش `## 14.3.0` را با توضیح تغییرات اضافه کنید. این متن
   همان چیزی است که مدیر سالن در صفحهٔ به‌روزرسانی می‌بیند.
3. تگ بزنید و بفرستید:

   ```text
   git tag v14.3.0
   git push origin v14.3.0
   ```

   یا از GitHub ← **Releases** ← **Draft a new release** همین تگ را بسازید.

GitHub Action به نام **Release** (`.github/workflows/release.yml`) خودکار:
آزمون‌ها را روی دیتابیس واقعی اجرا می‌کند، بستهٔ cPanel را می‌سازد
(`tools/build-release.php`)، اگر کلید امضا تعریف شده باشد امضایش می‌کند
و Release را با سه فایل منتشر می‌کند: `reshen-14.3.0.zip`، چکیدهٔ آن و
`manifest.json`. اگر آزمونی شکست بخورد، چیزی منتشر نمی‌شود.

همان ZIP برای نصب دستی هم قابل استفاده است.

### شماره‌گذاری نسخه

`اصلی.فرعی.اصلاحی` — مثل `14.3.1`.

- **اصلاحی و فرعی** (`14.3.0` ← `14.3.1` یا `14.4.0`): در حالت خودکار،
  شبانه نصب می‌شود.
- **اصلی** (`14.x` ← `15.0.0`): هرگز خودکار نصب نمی‌شود؛ مدیر باید
  یادداشت‌ها را بخواند و دکمه را بزند. تغییرات ناسازگار را برای نسخهٔ
  اصلی نگه دارید.
- **پیش‌انتشار** (`15.0.0-beta.1`): فقط هاست‌هایی که `UPDATE_CHANNEL=beta`
  دارند می‌بینند.

### امضای بسته (توصیه‌شده)

بدون امضا، به‌روزرسان فقط چکیدهٔ sha256 و HTTPS را بررسی می‌کند؛ یعنی
امنیت به امنیت حساب GitHub شما وابسته است. با امضا، حتی اگر کسی به حساب
GitHub دسترسی پیدا کند، بدون کلید خصوصی نمی‌تواند بسته‌ای بسازد که هاست‌ها
نصبش کنند.

1. روی رایانهٔ خودتان: `php tools/release-keygen.php`
2. کلید خصوصی را در GitHub ← Settings ← Secrets and variables ← Actions
   با نام `RESHEN_SIGNING_KEY` ذخیره کنید. جای دیگری نگهش ندارید.
3. کلید عمومی را در `.env` هر هاست بگذارید: `UPDATE_PUBLIC_KEY=…`

از این به بعد هاست بستهٔ بی‌امضا یا با امضای نادرست را نصب نمی‌کند.

### مخزن خصوصی

اگر مخزن را خصوصی کردید، یک توکن fine-grained فقط با دسترسی
**Contents: Read-only** روی همین مخزن بسازید و در `.env` هاست بگذارید:
`UPDATE_GITHUB_TOKEN=…`

## برای مدیر هاست

### کجا

**پنل پلتفرم ← به‌روزرسانی سامانه** (`/system/updates`). اگر هیچ مدیر
پلتفرمی تعریف نشده (نصب تک‌سالنی)، صاحب سالن همین صفحه را در منوی
«ابزارها»ی پنل سالن می‌بیند.

### حالت‌ها

| حالت | رفتار |
|---|---|
| نصب خودکار (پیش‌فرض) | هر ۶ ساعت بررسی؛ نسخهٔ فرعی/اصلاحی در بازهٔ شبانه (پیش‌فرض ۳ تا ۵ بامداد) نصب می‌شود |
| فقط اعلام | نسخهٔ تازه در منو علامت می‌خورد؛ نصب با دکمه |
| خاموش | بررسی خودکار نمی‌شود؛ دکمهٔ «بررسی همین حالا» کار می‌کند |

نصب خودکار با **کرون** انجام می‌شود (همان کرونی که پیامک یادآوری
می‌فرستد). اگر کرون تنظیم نشده، فقط نصب دستی کار می‌کند — راهنما در
`نصب.md`.

### هنگام به‌روزرسانی چه می‌شود

1. مانیفست و بسته از Release دریافت می‌شود؛ حجم، sha256 و (در صورت تنظیم)
   امضا بررسی می‌شود.
2. بسته در `storage/updates` باز می‌شود؛ مسیر ناامن (`../`، مسیر مطلق،
   symlink) یعنی رد کل بسته. هر فایل با فهرست چکیده‌های داخل بسته
   تطبیق داده می‌شود.
3. بررسی پیشاپیش: نسخهٔ PHP، دسترسی نوشتن روی همهٔ فایل‌ها، فضای دیسک.
4. اگر بسته مهاجرت دیتابیس تازه دارد، پشتیبان کامل دیتابیس در
   `storage/backups/…/database.sql.gz`.
5. سایت چند ثانیه «در حال به‌روزرسانی» (۵۰۳) نشان می‌دهد؛ هر فایلی که
   عوض یا حذف می‌شود اول در `storage/backups/…/files` کپی می‌شود.
6. مهاجرت‌ها اجرا می‌شوند و سایت با یک درخواست به `/health` آزموده
   می‌شود که باید با شمارهٔ نسخهٔ تازه پاسخ دهد.
7. هر خطا در ۵ و ۶ ← همهٔ فایل‌ها خودکار برمی‌گردند و آن نسخه دیگر
   خودکار امتحان نمی‌شود تا مدیر بررسی کند.

**هرگز دست نمی‌خورد:** `.env`، محتوای `storage` و `public/uploads` (عکس‌ها،
لوگوها، لاگ‌ها)، و هر فایلی که جزو بستهٔ قبلی نبوده است. فایل
`.htaccess`ی که دستی عوض کرده‌اید (مثلاً `RewriteBase`) بازنویسی نمی‌شود؛
نسخهٔ تازه کنارش با پسوند `.new` قرار می‌گیرد.

سه پشتیبان آخر نگه داشته می‌شوند.

### اگر مشکلی پیش آمد

- **به‌روزرسانی ناموفق:** فایل‌ها خودکار برگشته‌اند. «جزئیات فنی» همان
  ردیف در تاریخچه علت را می‌گوید.
- **مهاجرت نیمه‌کاره:** اگر مهاجرتی وسط کار شکست خورده، دکمهٔ «بازگردانی
  دیتابیس به پیش از این به‌روزرسانی» در همان ردیف هست. هرچه پس از آن
  لحظه ثبت شده از بین می‌رود؛ فقط وقتی سامانه خطا می‌دهد بزنید.
- **پردازه وسط کار کشته شد** (محدودیت زمان هاست): نیم ساعت بعد، کرون آن را
  تشخیص می‌دهد و فایل‌ها را از دفترچهٔ پشتیبان برمی‌گرداند. حالت
  نگه‌داری هم حداکثر پس از ۱۵ دقیقه خودش برداشته می‌شود.
- **دسترسی نوشتن نیست:** در cPanel ← File Manager دسترسی پوشه‌ها را ۷۵۵
  و فایل‌ها را ۶۴۴ کنید؛ مالک فایل‌ها باید همان کاربر cPanel باشد.

## تنظیمات `.env`

| کلید | پیش‌فرض | توضیح |
|---|---|---|
| `UPDATE_SOURCE` | `github` | یا `url` برای سرور انتشار خودتان |
| `UPDATE_GITHUB_REPO` | `Mmbz4378/barbar` | مخزن منبع |
| `UPDATE_GITHUB_TOKEN` | — | فقط برای مخزن خصوصی |
| `UPDATE_MANIFEST_URL` | — | برای `UPDATE_SOURCE=url`؛ نشانی HTTPS مانیفست |
| `UPDATE_CHANNEL` | `stable` | `beta` پیش‌انتشارها را هم می‌گیرد |
| `UPDATE_MODE` | `auto` | مقدار اولیه؛ از پنل قابل تغییر است |
| `UPDATE_WINDOW_START` / `_END` | `3` / `5` | بازهٔ نصب خودکار (ساعت به وقت سالن) |
| `UPDATE_PUBLIC_KEY` | — | کلید عمومی امضا؛ اگر باشد، امضا الزامی است |

## قالب مانیفست

```json
{
  "format": 1,
  "version": "14.3.0",
  "tag": "v14.3.0",
  "released_at": "2026-10-10T08:00:00+00:00",
  "min_php": "8.1.0",
  "notes": "…",
  "package": {"file": "reshen-14.3.0.zip", "url": "https://github.com/…/reshen-14.3.0.zip", "sha256": "…", "size": 1300000},
  "signature": "base64(Ed25519(\"reshen-release:1:14.3.0:<sha256>\"))"
}
```

داخل ZIP، فایل `VERSION` و `release-files.json` (فهرست همهٔ فایل‌ها با
sha256) هست؛ به‌روزرسان بعدی از همین فهرست می‌فهمد کدام فایل‌ها دیگر
لازم نیستند و باید حذف شوند.
